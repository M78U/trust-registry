# Persistent root chain and reviewed ledger migration

The existing v1 evidence record remains canonical byte-compatible: optional rootHistory is omitted for v1. For rotated records, rootHistory stores exact numbered root bytes before the final Root field. Verification replays the full chain from independent initial v1 SHA-256, at the recorded acceptance/build time for historical records and current UTC for loads. The ledger scans each record and requires exact previous root chain prefix, contiguous application sequence, immutable inventory/policy history and the existing review approval gate. All generations of TUF keys are checked against the pinned review authority on new builds. Root and application sequence are independent; no reset. Explicit bootstrap is still root/sequence 1 only.

For a rotated reviewed build use build-ledger with usual review and signing options, --root CURRENT.root.json --root-sha256 CURRENT_PIN, --initial-root-sha256 INITIAL_V1_PIN, repeat --root-chain 1.root.json --root-chain 2.root.json ... in order, and --expected-head LAST_LEDGER_RECORD_PIN (mandatory for root extension). Use new role signers and fresh snapshot approval. Subsequent rotated builds retain the full chain. Old v1 invocation remains valid. ledger-export --root-sha256 always takes the initial v1 pin, not the current root digest. Receipt includes rootVersion, initialRootSHA256 and current rootSHA256. Export includes every numbered root plus current signed metadata and target. Historical records never rewritten. Per-record bound increased for up to 32 historical roots; total ledger 256 MiB and 128 records unchanged.

Client refresh keeps private roots/1.root.json, roots/2.root.json, etc. under the existing state lock. Missing archive can be initialized only from exact pinned version-one cached bytes (legacy v1). Each numbered download is independently checked against the full chain via go-tuf UpdateRoot before it is written with a no-replacement hard link and passed to the upstream updater. Expired intermediate roots are allowed during update; final root must be current for successful refresh/installation. The cached root must equal the archive head byte-for-byte before and after refresh. Existing installed evidence must be a prefix of archive, and new installation must extend old installed history and application sequence; same sequence cannot change root or metadata. Offline load checks exact cache/evidence/archive agreement, current expiry and all signatures from initial pin. A v1-only old offline state can still load without an archive. No automatic fallback to earlier roots or rebuilding history from an unpinned rotated cache. If interrupted between archive and cache commits, ordinary refresh and load still fail closed; strict clients can use the explicit forward-only recovery below. Never remove the archive or reset trust. No hostile filesystem protection, directory fsync or anti-truncation external state if both archive and installed state are rolled back. Retain external head receipts. No production deployment or review-authority rotation. Review approval binds snapshot/dossier, not root/metadata choices; root rotation-specific governance and client-side release approval are still needed.

Tests cover v1 ledger then rotated sequence, export with initial pin, missing expected head rejection, v1 archive migration, local TLS rotated install/reload and truncated archive failure. No new dependencies. Automatic CI disabled and tests not executed.


## Explicit forward-only root cache recovery

If the numbered archive is complete but the mutable cached root is still an exact older archived root, an operator can use:

```sh
go run ./cmd/tuf-load --state STATE --root-sha256 INITIAL_V1_PIN \
  --authority AUTHORITY.json --authority-sha256 INDEPENDENT_AUTHORITY_PIN \
  --recover-root-cache --root-head-sha256 EXPECTED_ARCHIVED_HEAD_SHA256
```

SDK: `RecoverRootCache(RootRecoveryOptions{...})`. The selected head digest identifies the exact intended recovery destination; it is not a substitute for the independent initial root or authority pins. The operation validates state identity, holds the existing lock, verifies every consecutive old/new threshold-signed root and all role-key separation against the review authority, requires the installed root history to remain a prefix, and requires the current cached bytes to equal a numbered archived root. No missing, truncated, forked, unknown or malformed cached root is reconstructed. Already matching cache is an idempotent no-op. A complete synced temporary file is renamed into place; incomplete root staging files for new archive writes stay outside the numbered history.

Only root.json may change. Timestamp, Snapshot and Targets metadata, installation evidence, pending installation journal and the archive are not rewritten or removed. This is not a release approval or a restored installed Snapshot. Expired archived heads may be advanced only to resume online rotation; all normal expiry, public credential and rollback checks still apply to subsequent refresh/install and offline load. The report always requests a normal online refresh before relying on recovered state; supply the independently retained application checkpoint on that refresh. An old installed record whose root no longer equals current cache/archive remains unloadable. No network in recovery, no cloud operations, no automatic lock breaking, no guarantee of directory fsync/power-loss durability, no repair of other metadata or archive corruption. Research-mode recovery is intentionally not supported by this command. Do not manually clear metadata to force a refresh.

Integration coverage simulates archive-before-cache interruption, wrong head selection, unknown cached bytes, missing authority and lock refusal, exact preservation of timestamp, idempotence and subsequent strict update. These tests have been added but not executed locally.
