# TUF root rotation (experimental research)

The new SDK starts from exact independently pinned version-one root metadata bytes, accepts only consecutive numbered roots (max 33 roots, each 512000 bytes), and uses go-tuf v2.4.2 trustedmetadata.UpdateRoot for old and new root signature threshold verification. Each root must follow the strict four-role consistent-snapshot Ed25519 profile: unique role IDs and raw keys, no alias or unreferenced keys, up to 16 keys/role. Expired historical roots may be traversed, but final root must be valid at the explicit UTC evaluation time. This is a chain, not proof it is the latest online root. Keep an independent current root pin for rollback checks. This does not authorize CA anchors.

rotate-root requires the complete ordered current chain, independent initial and current root digests, current time, new expiry, explicit next four-role public-key configuration and old/new root signing thresholds. Local rotation creation requires a still-valid old root. Root version increases exactly one. Old/new authorized overlapping signers need only one signature on the shared new metadata. Retired online role keys are not accepted by new role signature checks. Keep private keys offline and separate; no key generation, remote signer, upload, automatic rotation or review-authority rotation. Historical versions must remain available to clients.

CLI (all flags precede positional arguments):
* verify-root-chain --root-chain 1.root.json --root-chain 2.root.json --initial-root-sha256 PIN1 --current-root-sha256 PIN2 --now CURRENT_RFC3339
* rotate-root with same chain and pins/time, --expires NEW_EXPIRY, --old-root-key OLD_PKCS8.pem, --root-key NEW_PKCS8.pem, --root-public NEW_ROOT_SPKI.pem, --targets-public TARGETS_SPKI.pem, --snapshot-public SNAPSHOT_SPKI.pem, --timestamp-public TIMESTAMP_SPKI.pem, --out NEW_NUMBER.root.json. Repeat keys and set role thresholds as appropriate.
* build-rotated uses the ordinary build flags, --root CURRENT_ROOT_FILE --root-sha256 CURRENT_PIN, plus --root-chain for every root in order and --initial-root-sha256 INITIAL_PIN. Creates fresh research staging with all numbered root metadata, current role-signed timestamp/snapshot/targets and exact snapshot target. Registry sequence and online metadata versions remain independent of root version (online versions equal Registry sequence).
* SDK VerifyRotatedRepository independently checks a staged in-memory repository against the full pinned chain, explicit current head pin, signed metadata links, current expiry and snapshot bytes. It shares existing offline evidence verification, returns TUFTargetAuthenticated only, not production trust. It does not persist or compare application sequence. Existing v1-only BuildRepository and installation/ledger APIs still reject rotated roots. Refresh already uses upstream TUF rotation, but rotated root cache is not yet an independently retained verified chain; do not treat Refresh as the new offline installation capability. No production migration or online publication in this PR.

Reviewed rotation and cross-generation key custody, persistent publisher root-history ledger, online client root-chain persistence and offline installed-state migration remain required. No real keys or CA data. Synthetic tests cover wrong old/new signer, expired intermediate vs final root, missing version, rollback, pin mismatch, retired signer, rotated repository signature chain and tampered timestamp. Tests not executed; automatic CI remains disabled.
